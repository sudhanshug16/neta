### G4 runtime

- **G4-1 the app cannot start a Node.** Symptom: launch the bundle with no
  Node running and it never connects; `ps` shows a new
  `NetaDesktop.app/Contents/Resources/neta node start --detach` every few
  seconds and `node.json` never appears. Root cause:
  `src/cli/commands/node.ts:99,104` re-spawns itself as
  `spawn(process.execPath, [process.argv[1], "node", "start"])`. In the
  `bun build --compile` executable the bundle ships as the exe, so
  `process.argv[1]` is the virtual path `/$bunfs/root/main`; the child then
  parses that as its command and exits with
  `neta: unknown command: /$bunfs/root/main`. Verified by running the argv
  by hand. `node dist/main.js node start --detach` is unaffected, which is why
  the CLI works and the app does not. Expected (docs/plan/08-cli.md T8.3 and
  the DoD item "Node autostarts from the app"): `--detach` returns once the
  Node is live. Owning path: `src/cli/commands/node.ts`.
- **G4-2 the launcher is re-spawned without bound.** Every failed
  `connect()` calls `launcher.start()` once
  (`Node/SocketNodeClient.swift:117-124,142-149`) and
  `NetaDesktopApp.swift:27-42` retries `connect()` in a 1 s loop forever, so a
  Node that cannot start leaves a growing trail of children (two live at a
  time, a new pair every five seconds, in the run above). Expected: one launch
  attempt, then a visible failed state. Owning path:
  `apps/macos/Sources/NetaDesktop/NetaDesktopApp.swift`,
  `Node/SocketNodeClient.swift`.
- **G4-3 notifications are split between two consumers, so half of every
  stream is lost.** This is the "not functional" symptom. Root cause:
  `SocketNodeClient.notifications` (`Node/SocketNodeClient.swift:80`) returns
  one `AsyncStream`, and two tasks consume it concurrently —
  `NetaDesktopApp.swift:32` folding into the `Store`, and
  `Chat/ChatViewModel.swift:56-62` filtering for `.turn`. An `AsyncStream`
  delivers each element to exactly one waiting consumer, so notifications
  alternate arbitrarily. `ChatViewModel` `continue`s past anything that is not
  a turn, dropping it for good. Measured with the probe: of one streamed reply,
  the store loop swallowed the turn-open, the first delta and the turn-end
  while the chat kept only the last delta; of four `mission.pin` `state`
  notifications, the store got two and the chat swallowed two. Expected
  (docs/plan/README.md Protocol summary, and the DoD "a prompt streams the
  leader's turn into the chat", "`neta_mission` puts a mission on the spine
  and in the bar within one notification"): every client component sees every
  notification. Owning path: `Node/SocketNodeClient.swift` plus the two
  consumers.
- **G4-4 no MCP tool can ever run: the Node does not serve the tool
  router.** `neta mcp`'s proxy forwards `tools/list` and `tools/call` to the
  Node as `tools.list` / `tools.call` (`src/tools/proxy.ts:199,218`), but
  `allHandlers` is only snapshot, registry, conversation and workspace
  (`src/node/lifecycle.ts:470-475`) and `createRouter`
  (`src/tools/router.ts:127`) is called from nothing but tests. Verified on the
  socket: `tools.list` answers
  `-32601 unknown method: tools.list (METHOD_NOT_FOUND)`. Consequence:
  `neta_mission`, the closeout tools and every other tool in 05 are
  unreachable at runtime, so no mission can be created, blocked or closed by a
  leader, and the DoD items about `neta_mission`, the blocked agent and the
  closeout fade cannot be tested at all. The missions in this check had to be
  seeded straight into the store. Owning path: `src/node/lifecycle.ts`,
  `src/tools/router.ts`.
- **G4-5 conversations are never persisted.** `conversation.tail` always
  returns `turns: [], blocks: []`, before and after a streamed reply. Root
  cause: the pump forwards ACP events to listeners only
  (`src/node/lifecycle.ts:332-350`); `appendTurn` and `appendBlock`
  (`src/store/conversations.ts:48`) are called from tests and nowhere in
  `src/`. Consequence: chat history is empty on every open and after every
  reconnect, the "re-tail for the current state" contract behind the bare
  end-of-turn ping (`:318-320`) cannot work, and 08's
  "`conversation.tail` for the last 20 blocks" is always empty. Expected
  (docs/plan/README.md Storage: `conversations/<sessionId>.ndjson`). Owning
  path: `src/node/lifecycle.ts`.
- **G4-6 the leader's session dies with the Node.** After any Node restart
  every prompt fails with `-32002 no such session: <sessionId>`, from the app
  and from the CLI alike. Root cause: `src/node/workspace-open.ts:155-158`
  reuses the stored `Leader` when one exists and only calls `createLeader`
  (which is what calls `acp.createSession`, `:111`) for a brand-new one, so the
  persisted `sessionId` names an ACP session that no longer exists. Since
  G4-1's autostart failure is itself a restart loop, a person who quits and
  reopens the app has a permanently mute leader. Expected (MANIFESTO Principle
  6 and 03's `resume: true`): the session is resumed or re-created at open.
  Owning path: `src/node/workspace-open.ts`, `src/node/lifecycle.ts`.
- **G4-7 the chat stops streaming after a reconnect and never restarts.**
  `connect()` calls `relay.renew()`, which finishes the old stream and makes a
  new one (`Node/SocketNodeClient.swift:110`, relay at `:498-520`).
  `ChatViewModel` captured the old stream in `start()`, so its `for await`
  ends and `streamTask` completes. `ChatPanel` calls `start()` only from
  `.task` and on a selection change (`Chat/ChatPanel.swift:58-63`), and the
  session id does not change across a reconnect. Expected: the chat follows
  the new connection. Owning path: `Node/SocketNodeClient.swift`,
  `Chat/ChatViewModel.swift`, `Chat/ChatPanel.swift`.
- **G4-8 the desktop cannot open a workspace.** `NodeClient`
  (`Node/NodeClient.swift:10-23`) has no `workspace.open`, and no Swift file
  mentions it. The app can only show workspaces some `neta` invocation opened
  first; on a clean machine it shows an empty window with no way forward.
  Expected (DoD item 2 "`workspace.open` works"): reachable from the app.
  Owning path: `Node/NodeClient.swift`, `Node/SocketNodeClient.swift`.
- **G4-9 the terminal chat repeats the whole reply.** `neta` with the fake
  agent's `STREAM` directive prints
  `First paragraphFirst paragraph continues.\n\nSecondFirst paragraph
  continues.\n\nSecond paragraph.`. Root cause: the Node re-sends the whole
  accumulated text in each delta under one `seq`, and `src/cli/chat.ts:168`
  writes every rendered block verbatim instead of replacing what it already
  printed for that `seq`. The desktop is right here — `ChatViewModel` files
  blocks by `seq` — so this is the CLI's alone. Expected
  (docs/plan/08-cli.md T8.4: text "written verbatim as it arrives"). Owning
  path: `src/cli/chat.ts`.
- **G4-10 a long `NETA_DIR` breaks the Node with a wrong error.** The socket
  is always `$NETA_DIR/node.sock` with no length guard
  (`src/store/paths.ts:57`, `src/node/lifecycle.ts:507`). Over the 104-byte
  `sun_path` limit, `bind` fails and Node reports
  `EADDRINUSE ... /node.sock` for a path that does not exist; `node start
  --detach` then reports only `timed out waiting for the node to start`,
  because the detached child's stderr goes to `ignore`
  (`src/cli/commands/node.ts:105-106`). Cost this check about twenty minutes.
  Expected: a clear error naming the real cause, and a detached start that
  surfaces why the child died. Owning path: `src/store/paths.ts`,
  `src/cli/commands/node.ts`.

  which answers and broadcasts a leader `state`.
- The fake agent launches from `settings.json` with `command`/`args` and
  `defaultModel`, and the three real providers can be turned off with
